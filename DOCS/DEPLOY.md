# Deploy notes — Sloth Drawer on Render

The deploy is deliberately **boring**: the container carries the scan's
verified result and serves it. No model, no Ollama, no DSN inside the image or
the repo. The cold-start story works because the boot path touches nothing
smarter than a SQLite file.

## Architecture at a glance

```
your laptop (podman)            Render (Containerfile build, free tier)
────────────────────────        ─────────────────────────────
sloth-drawer scan  ──out/──▶    deploy/seed/sloth.db (committed snapshot)
  (runs models locally)         └─ copied to /app/out/sloth.db at build
                                   uvicorn sloth_drawer.webapp:app
                                   GET /            device list
                                   GET /device/{s}  tasks + Mark done
                                   GET /device/{s}/card  the printable card
                                   GET /health      state-free liveness probe
```

`src/sloth_drawer/webapp.py` is the ASGI entry platforms point at (it does
exactly what `sloth-drawer serve` does — reads `SLOTH_HOME`, refuses to boot
without scan data). The web surface itself is unchanged: server-rendered HTML,
zero JavaScript.

## One-time / per-refresh: the seed

A free tier has no persistent disk, so the demo **state ships in the image**.
`deploy/build-seed.sh` copies `out/sloth.db` (your scan result) to
`deploy/seed/`, sanity-checks it for any DSN string, and tells you what to
commit. 3.5 MB and shrinking nothing.

```sh
# after any scan whose result you want on the demo:
deploy/build-seed.sh
git add deploy/seed && git commit -m "deploy seed: refresh scan snapshot"
git push
```

RULES.md compromise recorded: the DB files in `out/` are normally gitignored
("everything generated lives there"), but the deployed demo needs the state
available at image build time, so `deploy/seed/sloth.db` is an **explicit,
documented exception** — generated by the script above, never hand-edited,
checked by the script before committing. It contains no credentials and no
PDFs (the manuals are not ours to redistribute, RULES.md).

## Deploy (Render → Blueprint)

1. Push the repo (with `deploy/seed/sloth.db` committed) to GitHub.
2. In Render: **New → Blueprint**, select the repo. Blueprint looks for
   `render.yaml` at the repository root by default, so **set the Blueprint
   file path to `deploy/render.yaml`** — ours deliberately lives next to the
   Containerfile and the seed script (free plan, `./deploy/Containerfile`,
   health check `/health`). Render's own build executes the same instructions
   you run with podman locally — a Containerfile is build-tool-agnostic.
3. Deploy: first build runs `uv sync --frozen` — no compile steps, no cache
   poisoning; ~1-2 min. The boot is a `uvicorn` start reading one SQLite file.
4. Verify the cold start: hit the URL, wait >15 min idle, hit it again. The
   first request of a cold instance pays one container boot (~10-20 s);
   afterwards every page is one SQLite read.

### Local pre-ship check with Podman (the same thing Render will build)

```sh
# the seed must be current first:
deploy/build-seed.sh

# build and smoke-test the exact image Render will make:
podman build -f deploy/Containerfile -t sloth-drawer .
podman run --rm -p 8888:8000 sloth-drawer &
curl -s localhost:8888/health && curl -s -o /dev/null -w "%{http_code}\n" localhost:8888/
podman kill --signal=TERM --latest  # stop the background run
```

If `/health` returns `{"status":"ok"}` and the device list serves 200, what
Render builds will behave identically — the Containerfile contains no
platform-specific instructions.

## What the demo deliberately does NOT do in the cloud

- **No model calls.** The extraction, verification and retrieval experiments
  are machine-local (Ollama on device). Nothing in the boot path needs a GPU
  or a paid tier.
- **No Tiger DSN in the web service.** The web surface reads the local
  snapshot; the *retrieval* backend comparison is shown from the CLI and the
  parity run (`out/parity-run.txt`, 4/4 PARITY). If you later want the cloud
  retrieval live behind the web UI, that is a new route — and would mean
  putting the DSN in a Render env var (`render secrets set`), never in the
  repo or image.

## Rollback

Every deploy is an immutable image of a committed seed. Going back is the
revert button in Render's dashboard (or `git revert` the seed commit) — no
state to migrate, no database to roll.
